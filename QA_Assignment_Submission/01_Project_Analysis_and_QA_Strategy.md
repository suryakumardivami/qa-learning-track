# QA Assignment — Vendor Invoice Management Portal
## Document 01: Project Analysis & QA Strategy

## 1. Project Understanding

### What the Application Does

The **Vendor Invoice Management Portal** is a B2B enterprise web application that digitizes and automates the end-to-end invoice lifecycle between external vendors and an internal Accounts Payable (AP) team. It replaces manual, email-based invoice handling with a structured, auditable, role-controlled workflow — from invoice submission through to payment processing.

### Who the Users Are

| Role | Description |
|---|---|
| **Vendor** | External business partner who registers, logs in, and submits invoices against purchase orders |
| **AP Team Member** | Internal accounts payable staff who review, approve, or reject submitted invoices |
| **System** | Automated actor that sends email notifications and generates monthly reports |
| **Admin** *(implied)* | Internal user responsible for managing vendor registrations and user access |

### How the Workflow Operates

```
Vendor Registers → Vendor Logs In → Selects PO → Submits Invoice
         ↓
AP Team Reviews Invoice
         ↓
   ┌─────────────┐
   │  Approved   │──→ Forwarded to Payment Processing → Email to Vendor
   │  Rejected   │──→ Email to Vendor (with reason)
   └─────────────┘
         ↓
Monthly Invoice Activity Report Generated
```

**Detailed Steps:**
1. Vendor registers on the portal and is granted access (approval mechanism implied)
2. Vendor logs in and locates an existing Purchase Order (PO)
3. Vendor submits an invoice with relevant details and document attachment
4. Submitted invoice appears in the AP team's queue
5. AP team member reviews invoice details against PO
6. AP team member approves or rejects the invoice with comments
7. On approval: invoice is automatically forwarded to the payment processing system
8. Email notification is triggered at every status change
9. At month-end: system generates an invoice activity report covering all transactions

## 2. Assumptions

The following assumptions are made in the absence of explicit requirements documentation:

- Purchase orders are pre-created by the buyer/procurement team; vendors do not create POs
- Vendors must register and be approved before they can access the portal
- Each vendor can only view their own invoices; access to other vendors' data is restricted
- Invoice status flows sequentially: `Submitted → Under Review → Approved / Rejected`
- Approved invoices trigger an automatic forwarding event to the downstream payment system
- Email notifications are system-generated and not manually triggered by any user
- Only AP team members with the **Approver** role can approve or reject invoices
- A single level of approval is assumed unless otherwise specified
- The system maintains an audit trail for all approval/rejection actions
- Rejected invoices may be eligible for resubmission (to be confirmed — see Section 3)
- File uploads (invoice documents) are expected; accepted formats need clarification
- Monthly reports are auto-generated by the system on a scheduled basis
- The system is a web-based application accessible via browser

## 4. Risk Analysis

### 4.1 Business Risks

| Risk | Description | Likelihood | Impact |
|---|---|---|---|
| Duplicate invoice submission | Vendor submits same invoice twice, resulting in double payment | High | High |
| Over-invoicing | Invoice amount exceeds PO value without validation | Medium | High |
| Incorrect approval | AP user approves invoice due to insufficient data visibility | Low | High |
| Report inaccuracies | Monthly report totals mismatch actual approved/rejected counts | Medium | Medium |
| Partial invoice mismatch | Vendor invoices for items outside the PO scope | Medium | High |

### 4.2 Security Risks

| Risk | Description | Likelihood | Impact |
|---|---|---|---|
| Cross-vendor data access | Vendor A can view or manipulate Vendor B's invoices | Low | Critical |
| Privilege escalation | Vendor gains AP approval rights through URL or session manipulation | Low | Critical |
| Insecure file upload | Malicious file uploaded disguised as a valid invoice document | Medium | High |
| Session hijacking | Unauthorized session reuse after user logs out | Low | High |
| Brute-force login | Repeated login attempts to guess credentials | Medium | Medium |

### 4.3 Operational Risks

| Risk | Description | Likelihood | Impact |
|---|---|---|---|
| Email notification failure | Status changes not communicated to vendor or AP team | Medium | Medium |
| Payment forwarding failure | Approved invoice not reaching the payment system | Low | Critical |
| Session timeout during submission | Vendor loses unsaved invoice data mid-fill | Medium | Medium |
| High load during month-end | Report generation or submission slowdown at peak periods | Medium | Medium |

### 4.4 Data Risks

| Risk | Description | Likelihood | Impact |
|---|---|---|---|
| Incorrect status stored | Invoice status not updated correctly after AP action | Low | High |
| Invoice not linked to correct PO | Mismatch between invoice and associated purchase order | Low | High |
| Audit trail gaps | Approval/rejection actions not logged with user and timestamp | Medium | Medium |
| Data inconsistency post-payment | Portal shows different status than payment system | Low | High |

## 5. QA Strategy

### 5.1 What Will Be Tested

| Module | Testing Focus | Priority |
|---|---|---|
| Registration & Login | Functional, Security, Boundary | P1 |
| Invoice Submission | Functional, Validation, File Upload, Edge Cases | P1 |
| Invoice Approval / Rejection | Workflow, Role-Based Access, Concurrency | P1 |
| Payment Forwarding | Integration, Data Accuracy | P1 |
| Email Notifications | Integration, Error Handling | P2 |
| Monthly Reports | Data Accuracy, Access Control | P2 |
| Role-Based Access Control | Security, Authorization | P1 |
| API Endpoints | Functional, Authorization, Input Validation | P2 |
| Database Integrity | Record creation, status sync, audit trail | P2 |

### 5.2 Testing Types

**Functional Testing**
- Validate all happy-path flows for each module
- Verify all UI form validations (required fields, formats, limits)
- Confirm correct system behavior at each status transition

**Negative Testing**
- Invalid inputs across all form fields
- Boundary value testing (file size limits, invoice amounts at PO boundary)
- Invalid file formats for upload
- Missing required fields on submission

**Integration Testing**
- Email trigger on invoice status change
- Invoice forwarding to payment processing on approval
- Report data reflecting actual portal state

**Security Testing**
- Role-based access control: vendor vs AP vs admin
- Session management (timeout, logout, session token invalidation)
- File upload security (malicious file detection)
- Direct URL access without authentication

**Exploratory Testing**
- Real-world usage patterns and edge cases
- Concurrent user actions on the same invoice
- Browser back/forward behavior during multi-step workflows

**Database Validation**
- Invoice record created correctly on submission
- Status fields updated after approval/rejection
- Audit log entries present with user ID and timestamp

**API Validation**
- Correct HTTP status codes
- Authorization enforcement on all protected endpoints
- Input validation and error message quality

### 5.3 Entry & Exit Criteria

**Entry Criteria**
- Application deployed and accessible in test environment
- Test data ready: vendor accounts, AP accounts, active POs
- Test environment credentials provided

**Exit Criteria**
- All P1 (Critical) test cases executed and passed
- Zero open Critical or High severity defects
- All end-to-end workflows validated
- RTM shows 100% requirement coverage

## 7. Edge Cases

These are the scenarios most likely to be missed in standard testing but represent real-world failure points:

| # | Edge Case | Expected Behavior |
|---|---|---|
| 1 | Vendor submits duplicate invoice (same PO, same invoice number, same amount) | System blocks duplicate or prompts vendor to confirm |
| 2 | Network drops mid-file upload | Upload fails gracefully with clear error; no partial record created |
| 3 | Vendor uploads valid PDF with embedded malicious script | File is scanned and rejected or sanitized |
| 4 | Session expires while vendor is filling the invoice form | User is prompted to re-login; form data preserved if possible |
| 5 | Two AP users simultaneously click Approve on the same invoice | System applies optimistic locking; only one approval succeeds, other sees error |
| 6 | Vendor resubmits a rejected invoice with the same details unchanged | System either blocks identical resubmission or routes it for review again |
| 7 | Invoice date set to a future date | System validation rejects or flags future-dated invoices |
| 8 | Invoice date set far in the past (e.g., 2 years ago) | System validates date range and prompts for confirmation |
| 9 | AP user approves invoice while vendor cancels it simultaneously | System resolves race condition; most recent action wins with audit log entry |
| 10 | Monthly report generated during an active approval action | Report captures a consistent snapshot; partial states not included |
| 11 | Vendor account deactivated while invoice is under review | Invoice review continues; vendor receives no further portal access |
| 12 | PO is closed or cancelled after invoice is submitted | Invoice is flagged for manual review; not auto-rejected without AP action |

## 8. API Validation Thinking

Even without deep backend access, the following API behaviors should be validated:

| Endpoint | Validation Check |
|---|---|
| POST /login | Returns 200 + token on valid credentials; 401 on invalid; 429 on too many attempts |
| POST /invoices | Returns 201 on success; 400 on missing fields; 409 on duplicate invoice; 403 for vendor submitting to wrong PO |
| GET /invoices | Returns only invoices belonging to the authenticated vendor; 401 if unauthenticated |
| PUT /invoices/{id}/approve | Returns 200 on success; 403 if caller is not AP role; 409 if invoice already approved |
| PUT /invoices/{id}/reject | Returns 200 with reason; 400 if reason is missing; 403 if caller is not AP role |
| GET /reports/monthly | Returns 403 for vendor role; 200 with correct data for AP/admin role |
| POST /invoices (file upload) | Rejects unsupported MIME types; rejects files exceeding size limit; returns 413 for oversized files |

**Key checks:**
- All protected endpoints must return `401 Unauthorized` if no auth token is present
- All AP-only endpoints must return `403 Forbidden` for vendor tokens
- Error responses must include a meaningful message (not raw stack traces)
- Invoice ID in response must match the actual created record ID

## 9. Database Validation Thinking

The following spot-checks confirm data integrity behind the UI:

| Check | What to Verify |
|---|---|
| Invoice created | On submission, a record exists in the invoices table with correct vendor ID, PO ID, amount, and status = `Submitted` |
| Status update on approval | After AP approval, the invoice record status changes to `Approved` and `approved_by` field is populated |
| Status update on rejection | After AP rejection, status = `Rejected` and rejection reason is stored |
| Audit log entry | Each status change creates an entry in the audit/activity log with user ID, timestamp, and action |
| Payment record | On approval, a record in the payment queue table is created with the invoice reference |
| Notification log | Email notification events are logged with invoice ID, recipient, event type, and send status |
| Duplicate check | No two records share the same invoice number, vendor ID, and PO ID combination |

## 10. Security Validation

| Check | Test Action | Expected Result |
|---|---|---|
| Unauthenticated access | Access /invoices, /approve, /reports directly without login | Redirected to login page; 401 returned by API |
| Vendor cross-access | Vendor A manipulates URL to access Vendor B's invoice ID | 403 Forbidden; no data returned |
| Vendor accessing AP pages | Vendor navigates to /ap/invoices/approve via direct URL | Access denied with appropriate message |
| Brute force login | Submit 10+ failed login attempts for same account | Account locked or rate-limited; CAPTCHA or lockout message shown |
| Session invalidation on logout | Log out, then use browser back button and try to act on invoice | Session invalid; redirected to login |
| Malicious file upload | Upload a file with .pdf extension but containing a script | File rejected or sanitized; no execution on server |
| SQL injection | Enter `' OR 1=1 --` in login email or invoice fields | Input sanitized; no unintended data returned |
| Sensitive data exposure | Check API responses for unnecessary PII or internal IDs | Only required fields returned; no stack traces in error responses |

## 11. Recommendations

These are practical improvements that would meaningfully reduce risk in production:

1. **Duplicate Invoice Detection** — Implement server-side duplicate detection based on (vendor ID + PO ID + invoice number) combination before persisting the record
2. **Invoice Locking on Review** — When an AP user opens an invoice for review, lock it to prevent concurrent approval conflicts; display a "currently being reviewed by [User]" message to others
3. **Email Retry Mechanism** — Implement automatic retry with exponential backoff for failed email deliveries; log failures for manual follow-up
4. **Audit Trail Enforcement** — Every approval, rejection, and resubmission action must log the acting user's ID and timestamp; this is non-negotiable for financial applications
5. **Clear Validation Messages** — Replace generic "Invalid input" errors with specific messages indicating exactly which field failed and why
6. **File Upload Scanning** — MIME type validation alone is insufficient; integrate basic file content inspection to reject disguised malicious files
7. **Session Timeout Warning** — Warn the vendor 2–3 minutes before session expiry while filling the invoice form, with an option to extend the session
8. **Invoice Amount Alert** — When invoice amount approaches or exceeds the PO value, display a clear warning to the vendor before submission (not just block it silently)
